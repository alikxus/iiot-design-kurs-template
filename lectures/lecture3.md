# Лекція 3. Збереження телеметрії: часові ряди

**Тиждень 3 · 2 академічні години · лабораторна: ingest у SQLite, агрегація, retention**

## Мета
Спроєктувати схему зберігання часових рядів, оцінити обсяги і побудувати конвеєр «MQTT → база» з пакетним записом, агрегацією та політикою зберігання.

## 1. Особливості часових рядів
- Запис майже завжди **append-only**, у порядку часу.
- Читання — **діапазонами часу** («остання година», «вчора») та агрегатами.
- Дані **старіють**: сирі потрібні тижні, агрегати — роки.
- Обсяги великі й передбачувані → можна оцінити заздалегідь.

## 2. Вибір сховища

| Варіант | Коли обирати |
|---|---|
| SQLite / PostgreSQL | прототип, невеликі обсяги, потрібен SQL і транзакції |
| TimescaleDB (розширення PostgreSQL) | SQL + автоматичне секціонування `hypertable`, стиснення, continuous aggregates |
| InfluxDB | вузькоспеціалізована TSDB, зручна модель `measurement/tags/fields`, власні мови запитів |
| Parquet/об'єктне сховище | довгий архів, аналітика пакетами |

У лабораторній використовуємо **SQLite** (без встановлення сервера), але структуру проєктуємо так, щоб міграція була тривіальною.

### Приклад для InfluxDB (line protocol)
```
telemetry,device=pump-01,site=kyiv vibration=1.82,temperature=55.3 1760000000000000000
```
Теги — індексовані (низька кардинальність: пристрій, майданчик); поля — значення. **Не кладіть у теги значення, що швидко змінюються** (кардинальність вибухає).

### Приклад для TimescaleDB
```sql
CREATE TABLE telemetry(ts timestamptz NOT NULL, device_id text NOT NULL, metric text NOT NULL, value double precision NOT NULL);
SELECT create_hypertable('telemetry', 'ts');
CREATE INDEX ON telemetry (device_id, metric, ts DESC);
```

## 3. Схема: «довга» чи «широка»

- **Довга** (`ts, device, metric, value`): гнучка, нові метрики без міграції, але більше рядків.
- **Широка** (`ts, device, vibration, temp, ...`): компактніша, швидша для читання кількох метрик разом, але зміна метрик = зміна схеми.

У курсі — довга схема. Індекс: `(device_id, metric, ts)` відповідає основному запиту «останні N значень метрики пристрою».

```sql
CREATE TABLE telemetry(ts REAL NOT NULL, device_id TEXT NOT NULL, metric TEXT NOT NULL, value REAL NOT NULL);
CREATE INDEX ix_tel ON telemetry(device_id, metric, ts);
```

## 4. Оцінка обсягів (обов'язковий крок проєктування)

Приклад: 100 агрегатів × 1 повідомлення/с × 4 метрики.
- Повідомлень на добу: 100 × 86 400 = 8,64 млн.
- Рядків (довга схема): 8,64 млн × 4 = 34,56 млн/добу.
- При ~40 байт/рядок (з індексом реально більше): ≈ 1,4 ГБ/добу ≈ 500 ГБ/рік **сирих** даних.

Висновок: потрібні (а) агрегація, (б) retention, (в) стиснення/секціонування. Зменшення частоти запису до 1 раз на 10 с зменшує обсяг у 10 разів — часто достатньо для повільних величин (температура).

## 5. Пакетний запис (batching)

Вставка по одному рядку — головне «вузьке місце». Накопичуємо пачку (за кількістю **або** за часом) і пишемо однією транзакцією:

```python
with conn:
    conn.executemany("INSERT INTO telemetry VALUES (?,?,?,?)", rows)
```

Компроміс: більша пачка → вища пропускна здатність, але більша затримка і більший обсяг втрат при падінні процесу. Тому — і порогове значення, і періодичний `flush()`.

**Ідемпотентність**: MQTT QoS 1 може дублювати. Варіанти: унікальний ключ `(device_id, metric, ts)` + `INSERT OR IGNORE`, або терпіти дублікати й усувати їх при агрегації.

## 6. Агрегація (downsampling)

Хвилинні агрегати зберігають `avg, min, max, n` — достатньо для графіків і трендів.

```sql
INSERT OR REPLACE INTO telemetry_1m
SELECT CAST(ts/60 AS INTEGER)*60, device_id, metric, AVG(value), MIN(value), MAX(value), COUNT(*)
FROM telemetry WHERE ts < :before GROUP BY 1, device_id, metric;
```

`INSERT OR REPLACE` + первинний ключ `(bucket, device_id, metric)` робить завдання **ідемпотентним** — його безпечно запускати за розкладом повторно. Важливо агрегувати лише **закриті** відра (`ts < before`), інакше неповна хвилина дасть хибне середнє.

## 7. Retention (політика зберігання)

Приклад політики: сирі — 14 діб; хвилинні — 2 роки; погодинні — 10 років. Видалення старих сирих даних — окреме завдання **після** успішної агрегації.

```python
def purge_older_than(conn, ts):
    with conn:
        return conn.execute("DELETE FROM telemetry WHERE ts < ?", (ts,)).rowcount
```

## 8. Якість даних
- Час: зберігати UTC; перевіряти розбіжність годинників пристрою і сервера.
- Пропуски: відрізняти «немає даних» від «нуль».
- Схема й одиниці: версія схеми в повідомленні, одиниці у назві метрики.
- Погані повідомлення не повинні зупиняти конвеєр: логувати й пропускати (але лічити).
