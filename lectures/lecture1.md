# Лекція 1. Архітектура IIoT-систем та вимоги до них

**Лабораторна: ТЗ та симулятор насосного агрегату**

## Мета
Навчитися описувати індустріальну систему інтернету речей (IIoT) на рівні архітектури: рівні, потоки даних, вимоги; перетворювати вимоги на технічне завдання (ТЗ).

## 1. Що таке IIoT і чим він відрізняється від «побутового» IoT

| Критерій | Споживчий IoT | Індустріальний IoT |
|---|---|---|
| Ціна відмови | незручність | простій лінії, аварія, ризик для людей |
| Строк життя пристроїв | 2–5 років | 10–25 років |
| Мережа | Wi-Fi, BLE | Ethernet, RS-485, 4G/5G, LoRaWAN, OPC UA |
| Доступність | «кращі зусилля» | 99,9–99,999 % |
| Безпека | пароль у застосунку | сегментація, IEC 62443, аудит |
| Протоколи | довільні | стандартні: Modbus, OPC UA, MQTT |
| Детермінізм | не потрібен | часто потрібен (контур керування) |

Ключова ідея курсу: IIoT не замінює АСУ ТП, а **надбудовується** над нею — збирає дані, аналізує, дає сервіси (моніторинг, прогноз, оптимізація). Контур регулювання лишається на ПЛК.

## 2. Піраміда автоматизації (ISA-95) та її «розплющення»

- Рівень 0 — датчики й виконавчі механізми (процес).
- Рівень 1 — ПЛК, контролери.
- Рівень 2 — SCADA/HMI.
- Рівень 3 — MES (виробничі операції).
- Рівень 4 — ERP (бізнес).

IIoT додає **горизонтальний шлях даних** «рівень 0/1 → edge → хмара/дата-центр», який обходить жорстку ієрархію: дані з датчиків вібрації можуть йти напряму в аналітику, не зачіпаючи SCADA.

## 3. Еталонні архітектури

**RAMI 4.0** (Industrie 4.0): тривимірна модель.
- Вісь *Layers*: Asset → Integration → Communication → Information → Functional → Business.
- Вісь *Life Cycle & Value Stream*: тип/екземпляр, розробка/виробництво/експлуатація.
- Вісь *Hierarchy Levels*: Product, Field Device, Control Device, Station, Work Centers, Enterprise, Connected World.

**IIRA** (Industrial Internet Consortium): чотири точки зору — *business, usage, functional, implementation*; п'ять функціональних доменів — *control, operation, information, application, business*.

Практичний висновок: перед вибором технологій відповісти на чотири питання — **що** є активом, **які** дані потрібні, **де** вони обробляються, **хто** їх споживає.

## 4. Edge / Fog / Cloud

| Шар | Де | Затримка | Типові задачі |
|---|---|---|---|
| Device | на машині | мс | вимірювання, первинна фільтрація |
| Edge | шафа/цех | 10–100 мс | протокольна трансляція, буферизація, правила, локальний ML |
| Fog/On-prem | серверна підприємства | 0,1–1 с | збереження, дашборди, інтеграція з MES |
| Cloud | дата-центр | 0,1–кілька с | довгострокова аналітика, навчання моделей, флот-рівень |

**Правило вибору місця обробки**: чим жорсткіша вимога до затримки/автономності й чим більший обсяг сирих даних — тим ближче до джерела. Агреговані дані й складні моделі — вгору.

## 5. Наскрізний сценарій курсу: насосна станція

Станція має кілька насосних агрегатів. Кожен агрегат: датчик вібрації (мм/с RMS), температури підшипника (°C), тиску на виході (бар), струм двигуна (А).

Бізнес-цілі: (1) бачити стан у реальному часі, (2) отримувати сповіщення про відхилення, (3) прогнозувати знос підшипника та планувати ремонт, (4) мати журнал для аудиту.

**Архітектура, яку ми будуватимемо за 7 тижнів:**

```
[Pump simulator] -> [Edge gateway] --MQTT--> [Broker] --> [Ingest -> TSDB]
                                                  |-----> [Alert engine -> alerts topic]
                                                  '-----> [Analytics: anomalies, RUL]
```

## 6. Вимоги

**Функціональні (FR)** — що система робить. Приклад: FR-1 «Шлюз публікує телеметрію кожного агрегату з періодом ≤ 1 с».
**Нефункціональні (NFR)** — як добре: продуктивність, доступність, безпека, супровідність. Приклад: NFR-1 «Втрата даних при розриві зв'язку до 10 хв — 0 %».

Хороша вимога **вимірювана** та **перевірювана**:
- ✗ «Система має бути швидкою».
- ✓ «Від вимірювання до сповіщення — не більше 3 с (p95)».

Шаблон розділів ТЗ: мета; межі системи; стейкголдери; FR; NFR; інтерфейси; обмеження; критерії приймання; ризики.

## 7. Моделювання пристроїв

Коли фізичного стенда немає (наш випадок), пишемо **симулятор** — він також корисний у реальних проєктах для тестів і демо.

Хороший симулятор: детермінований (seed), параметризований (знос, несправності), видає той самий формат, що й реальний пристрій.

Мінімальна модель з шумом і дрейфом:

```python
import random
rng = random.Random(42)
wear = 0.0
for step in range(5):
    wear += 0.01
    vibration = 1.8 + 6.0 * wear + rng.gauss(0, 0.15)   # мм/с
    print(round(vibration, 3))
```

Формат повідомлення (контракт даних):

```json
{"device_id": "pump-01", "ts": 1760000000.0, "running": true,
 "metrics": {"vibration_mm_s": 1.84, "temperature_c": 55.2, "pressure_bar": 4.19, "current_a": 12.1}}
```

Правила контракту: UTC-час у вигляді epoch; одиниці — у назві поля; усі значення — числа; поля не перейменовуємо без версії схеми.
