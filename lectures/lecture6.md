# Лекція 6. Кібербезпека та надійність IIoT

**Лабораторна: автентифікація, ACL, підпис повідомлень, reconnect**

## Мета
Навчитися будувати модель загроз для IIoT, застосовувати базові механізми захисту (автентифікація, авторизація, шифрування, цілісність) та проєктувати відмовостійкі клієнти.

## 1. Чому IIoT вразливий
- Довгий життєвий цикл обладнання → застаріле ПЗ без оновлень.
- Раніше «ізольовані» мережі отримали вихід у IT/хмару.
- Пріоритет доступності над конфіденційністю: не можна просто «перезавантажити».
- Наслідки — фізичні (аварії, екологія, безпека людей).

**Тріада CIA** + для OT важливо **Safety**: пріоритет — доступність і цілісність, потім конфіденційність.

## 2. Стандарти та сегментація
**IEC 62443** — серія стандартів з безпеки промислових систем: ключові поняття — **зони** (групи активів із однаковими вимогами) та **канали/conduits** (контрольовані зв'язки між зонами), рівні безпеки SL 1–4.

**Модель Перде / ISA-95 + DMZ**: між OT (рівні 0–3) та IT (4–5) — демілітаризована зона; **односпрямовані** шлюзи (data diode) для найкритичніших ділянок. IIoT-шлюз — це точка контрольованого переходу, тому його захищають особливо.

## 3. Модель загроз (STRIDE)
| Загроза | Приклад в нашій системі | Контрзахід |
|---|---|---|
| Spoofing (підміна) | зловмисник видає себе за pump-01 | автентифікація (пароль/сертифікат) |
| Tampering (зміна) | змінено значення вібрації «в дорозі» | TLS, підпис повідомлень |
| Repudiation (відмова) | «я не надсилав команду» | журнал, підпис |
| Information disclosure | прослуховування Wi-Fi | TLS |
| Denial of service | флуд брокера | ліміти, квоти, сегментація |
| Elevation of privilege | пристрій пише у чужий топік | ACL (мінімальні права) |

## 4. Автентифікація й авторизація в MQTT

**Автентифікація**: логін/пароль (мінімум), **сертифікати X.509 (mTLS)** (краще для флоту), токени (MQTT 5 enhanced auth).
**Авторизація (ACL)**: кожен клієнт — лише своє. Мінімальні права:

```
user pump-01
topic write plant/+/+/pump-01/#

user ingest
topic read plant/#

user alerts
topic read plant/+/+/+/telemetry
topic write plant/+/+/+/alerts
```

Конфіг Mosquitto:

```
listener 1883
allow_anonymous false
password_file /mosquitto/config/passwd
acl_file /mosquitto/config/acl
```

Створення пароля: `mosquitto_passwd -b passwd pump-01 <пароль>`. Для продакшену — **TLS на порту 8883** (`cafile`, `certfile`, `keyfile`), унікальні секрети на пристрій, ротація.

> Попередження: у навчальних прикладах пароль = `ім'я-pw`. У реальній системі секрети **не зберігаються в коді та репозиторії** — лише у менеджері секретів/змінних середовища.

## 5. Цілісність і захист від replay на рівні застосунку
TLS захищає канал «клієнт—брокер», але не «пристрій—споживач» наскрізно (брокер бачить усе). Додатковий шар — **HMAC-підпис** повідомлення спільним секретом:

`sig = HMAC-SHA256(secret, topic ‖ ts ‖ nonce ‖ canonical_json(payload))`

Перевірка: (1) підпис збігається (порівняння **сталого часу**, `hmac.compare_digest`); (2) `|now − ts| ≤ max_age`; (3) `nonce` не бачили в межах TTL (захист від повтору перехопленого повідомлення).

```python
import hmac, hashlib, json

def canon(payload):
    return json.dumps(payload, separators=(",", ":"), sort_keys=True)

def mac(secret: bytes, topic, ts, nonce, payload):
    data = f"{topic}\n{ts}\n{nonce}\n{canon(payload)}".encode()
    return hmac.new(secret, data, hashlib.sha256).hexdigest()

ok = hmac.compare_digest(received_sig, mac(secret, topic, ts, nonce, payload))
```

Підпис включає **топік**: так повідомлення від pump-01 не можна «перекинути» у топік pump-02.

Обмеження HMAC: спільний секрет → хто може перевірити, той може й підробити; для неспростовності потрібні асиметричні підписи (Ed25519/ECDSA).

## 6. Надійність і відмовостійкість

**Доступність у числах**: 99,9 % → ≈ 8,76 год простою на рік; 99,99 % → ≈ 52,6 хв; 99,999 % → ≈ 5,3 хв.

**Патерни:**
- **Store-and-forward** на edge (лекція 2).
- **Reconnect з експоненційною затримкою та джитером**: затримки 1, 2, 4, 8 … до стелі; джитер ±20 % розносить у часі «шторм» одночасних перепідключень після відновлення брокера.
- **Ідемпотентність** споживачів (QoS 1 → дублікати).
- **Health-check** кожного сервісу; перезапуск за політикою (`restart: unless-stopped`).
- **Деградація**: втрата аналітики не повинна зупиняти збір.
- **Резервування брокера**: кластер/міст (bridge) для критичних майданчиків.

```python
import random

def backoff_delays(base=1.0, factor=2.0, cap=60.0, jitter=0.0, rng=None):
    rng = rng or random
    d = base
    while True:
        yield min(d, cap) * (1 + rng.uniform(-jitter, jitter)) if jitter else min(d, cap)
        d = min(d * factor, cap)
```

## 7. Чек-ліст «мінімально безпечного» IIoT
1. Немає анонімного доступу; унікальні облікові дані на пристрій.
2. ACL за принципом мінімальних прав.
3. TLS між усіма зонами.
4. Секрети поза репозиторієм; можливість ротації.
5. Підпис/перевірка критичних повідомлень і команд.
6. Журнал подій безпеки; моніторинг невдалих входів.
7. Сегментація мережі; відсутність прямого виходу пристроїв в інтернет.
8. Процес оновлення ПЗ пристроїв.
